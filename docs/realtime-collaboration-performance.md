# 实时协作性能优化报告：Pusher Cloud 与本地 Soketi

> 测试日期：2026-08-20  
> 测试环境：Next.js 16 开发模式、Windows、本地 PostgreSQL、同一浏览器与问卷操作流程  
> 测试范围：实时连接、Presence 订阅、频道鉴权、题目创建事件发布与客户端接收

## 1. 背景与目标

第一阶段已经将题目创建改为乐观更新，并将实时广播移出用户响应关键路径。本阶段继续处理仍然存在的外部网络开销：开发环境连接云端 Pusher 时，数据库写入只需数毫秒，但一次暖广播通常仍需约 200 ms，且偶尔出现超过 600 ms 的抖动。

本阶段目标：

1. 在不修改云端 Pusher 凭据的前提下，支持开发环境切换到本地 Soketi；
2. 使用相同埋点对比云端与本地实时链路；
3. 让所有编辑类接口不再同步等待实时广播；
4. 保持 PostgreSQL 为最终事实来源，并为广播失败提供可追踪日志。

## 2. 测试方法

两组测试均采用同一操作流程：

1. 重启 Next.js 开发服务器并打开同一问卷编辑页；
2. 记录首次连接与 Presence Channel 订阅；
3. 连续新增 6 道文本题；
4. 第一次新增作为冷启动观察值，后 5 次计算暖请求中位数；
5. 通过同一个 `requestId` 关联服务端发布与浏览器接收日志。

测试指标：

- **连接建立**：Pusher 客户端创建到 WebSocket 连接成功；
- **Presence 订阅**：开始订阅到 `subscription_succeeded`；
- **频道鉴权**：`/api/pusher/auth` 业务处理总时长；
- **事件发布**：服务端 SDK 调用开始到实时服务确认完成；
- **事件送达**：事件时间戳到当前浏览器收到事件。

开发模式下的 Turbopack 首次编译时间不计入暖请求中位数。

## 3. 结果

### 3.1 同口径对比

| 指标                       | 云端 Pusher | 本地 Soketi |       变化 |      倍数 |
| -------------------------- | ----------: | ----------: | ---------: | --------: |
| WebSocket 连接建立         |    450.4 ms |     54.2 ms | **-88.0%** |  **8.3×** |
| Presence 订阅成功          |    861.5 ms |    183.4 ms | **-78.7%** |  **4.7×** |
| 频道鉴权（暖）             |     54.7 ms |     55.6 ms |      +1.6% |    约等于 |
| 服务端事件发布（暖中位数） |    220.6 ms |      6.4 ms | **-97.1%** | **34.5×** |
| 事件送达浏览器（暖中位数） |    158.0 ms |     72.0 ms | **-54.4%** |  **2.2×** |

### 3.2 发布样本

| 提供方       |    冷启动 | 暖样本                               |     暖中位数 |
| ------------ | --------: | ------------------------------------ | -----------: |
| Pusher Cloud | 1293.7 ms | 220.6、219.5、628.8、210.0、221.4 ms | **220.6 ms** |
| Soketi Local |    9.5 ms | 5.6、4.7、7.5、7.1、6.4 ms           |   **6.4 ms** |

本地事件发布不仅更快，样本也更集中。云端组出现 628.8 ms 暖请求抖动；本地组全部位于 4.7–7.5 ms。

### 3.3 结果解释

频道鉴权几乎没有变化是符合预期的。该接口主要执行 NextAuth 会话解析和 PostgreSQL 权限查询，`authorizeChannel` 本身在两组测试中都小于 1.2 ms，因此它不是实时服务网络延迟。

本地发布为 6.4 ms，而浏览器事件送达为 72.0 ms。后一个指标还包含 `after()` 调度、HTTP 响应收尾、WebSocket 分发以及浏览器主线程调度，因此不能将两者直接相减解释为 Soketi 的纯网络耗时。

## 4. 实现方案

### 4.1 云端与本地可切换

保留原有云端 Pusher 配置，并新增两个显式开关：

```env
REALTIME_PROVIDER=soketi
NEXT_PUBLIC_REALTIME_PROVIDER=soketi
```

开发环境使用固定的本地凭据连接 `127.0.0.1:6001`；切回 `pusher` 并重启开发服务器即可恢复云端方案。云端密钥无需覆盖或删除。

### 4.2 本地服务生命周期

```bash
pnpm realtime:up
pnpm realtime:logs
pnpm realtime:down
```

Soketi 容器是无状态的：问卷、题目、锁定信息仍存储在 PostgreSQL，停止容器不会删除业务数据。

### 4.3 共享协议与服务端实现分离

事件名称和 TypeScript 类型移动到浏览器与服务端都可安全引用的共享模块。Pusher 服务端 SDK、凭据和发布逻辑仅保留在服务端模块，避免服务端依赖进入浏览器构建。

### 4.4 广播退出响应关键路径

以下操作现在都在数据库成功后立即响应，并通过 Next.js `after()` 完成实时通知：

- 题目创建、更新、删除与排序；
- 问卷基本信息更新；
- 单题锁定、解锁和批量解锁；
- 协作者离开后的解锁通知。

每次后台广播统一输出：

- `requestId`
- `provider`
- `operation`
- `event`
- `duration`

失败时输出 `[Realtime Broadcast Error]`。广播失败不会回滚已经提交的数据库操作；客户端刷新或重新连接后从数据库恢复最新状态。

## 5. 结论

本地 Soketi 适合作为开发环境实时服务：它将暖广播中位数从 220.6 ms 降至 6.4 ms，减少 97.1%，同时显著降低连接、订阅和事件回传延迟。开发过程不再受公网距离和云服务抖动干扰，实时协作调试的反馈更稳定。

生产环境本阶段仍保留 Pusher Cloud。自托管实时服务需要额外承担高可用、监控、扩缩容和升级维护，不能仅凭本机延迟数据直接替换生产方案。

## 6. 后续建议

1. 用两个浏览器会话验证题目更新、删除、排序和锁定/解锁的跨客户端一致性；
2. 为 `[Realtime Broadcast Error]` 接入生产日志或告警平台；
3. 若未来评估生产自托管，补充并发连接、断线重连、多实例 Pub/Sub 和故障恢复测试；
4. 视鉴权流量决定是否精简权限查询字段或增加短时权限缓存。
