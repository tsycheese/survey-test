完整叙事

一开始，我们看到的是“添加题目很慢”；计时后发现，真正的问题是所有步骤被串在用户等待路径上。于是先通过乐观更新把交互反馈提前，再通过查询合并和快路径压缩持久化时间。

本地 PostgreSQL 随后暴露出云端实时服务成为开发环境的新主导延迟，因此引入兼容 Pusher 协议的本地 Soketi。系统变成“先本地、后持久化、再广播”后，性能问题也转化成分布式状态问题：锁属于谁、重排是否原子、自己的广播是否重复应用、断线期间遗漏的变化如何找回。

后续提交分别用作用域与事务、幂等 mutation ID、重连快照对账解决这些风险，最后通过双账号、断网和并发操作验证闭环。价值不只是一组更快的毫秒数，而是完成了诊断、重构、基础设施、正确性设计和验收的全流程。

简历表述参考

重构多人协作问卷编辑器的题目创建链路，引入乐观更新、临时 ID、串行持久化、幂等 mutation ID、事务化重排与断线快照对账；在本地 PostgreSQL 暖请求基准中将用户可见延迟中位数由 379.2 ms 降至 73.7 ms（-80.6%），服务端关键路径由 210.3 ms 降至 17.5 ms（-91.7%），并通过双账号并发与断线恢复测试验证最终一致性。
