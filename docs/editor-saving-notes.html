最近，我把编辑器的“保存”重新想了一遍

这不是一次界面提示的小修补。真正的变化是：保存不再是一组散落的请求， 而是一条能观察、能排队、失败后还能继续处理的状态链路。

从“发出去就算保存”，走到了“我知道它现在在哪一步，也知道失败后怎么办”。

给之后回看这段代码的自己
01 / change

先说变化：从散装请求到统一 Mutation

以前每个操作各自调用接口，看起来直接，但在连续编辑、网络失败和多人协作时， 很难回答“哪份内容才是最新的”。

之前容易发生的事

  • 后发请求先返回，旧内容最后落库。
  • 排序和普通修改互相覆盖，结果偶尔不可信。
  • 保存失败只是一声提示，本地草稿可能跟着对账消失。
  • 标题、描述、题目和设置各有一套保存感觉。
  • 界面说“已保存”，但这个词并不覆盖整个问卷。

现在形成的约束

  • 同一资源的操作进入同一条串行队列。
  • 题目内容和题目结构分别使用修订号。
  • 失败与冲突会保护本地草稿，并阻止危险离开。
  • 实时事件只提示“数据失效”，最终用服务器快照对账。
  • 顶部状态栏成为正常保存状态的唯一出口。
02 / flow

我现在如何理解这条保存链路

可以把它记成五个动作。每一层只解决一类问题，不让界面、网络和协作状态混成一团。

本地草稿 输入先落到 store，界面不等待网络。
资源队列 题目、排序、问卷详情各自串行执行。
服务端校验 检查权限、锁、题目或结构修订号。
提交基线 成功后更新持久化版本，不覆盖更新的草稿。
快照对账 实时通知后重新读取服务器的最终事实。
L1

乐观编辑负责“手感”

输入、拖动、新增先在本地呈现。网络失败不会让用户刚刚输入的内容突然消失。

L2

Keyed Queue 负责“先后”

question:id、survey-order:id、 survey-details:id 分开排队，互不阻塞，但同一资源绝不乱序。

L3

Revision 负责“过期判断”

题目内容使用 revision，题目集合和顺序使用 structureRevision，问卷详情使用 detailsRevision。陈旧请求不能悄悄覆盖新结果。

L4

Reconcile 负责“最终一致”

实时广播不直接拼装本地状态，而是触发快照刷新；若本地仍在保存或失败，草稿会被保护。

03 / cases

几个操作，各自靠什么保证

它们看上去都叫“保存”，实际面对的风险并不一样，所以保护方式也不同。

新增题目

怕重复，不怕冲突

临时题目立即出现；请求携带唯一操作 ID。即使网络重试，服务端也只创建一次，并返回当前结构修订号。

修改题目

怕旧内容覆盖新内容

保存时提交预期 revision，服务端同时检查题目锁。失败保留草稿；冲突时可以保留我的修改或恢复服务器版本。

题目排序

怕整组结构被陈旧顺序覆盖

提交完整、连续的题目序列和 structureRevision，服务端在事务内更新全部顺序。

问卷详情

怕标题、描述和设置相互乱序

三者共用 survey-details 队列和 detailsRevision。文本输入防抖，失焦立即刷新；设置变更立即保存，冲突时可以选择保留本地修改或恢复服务器版本。

04 / ux

状态提示应该安静，但不能含糊

正常保存是全局事实，放在顶部即可；异常才需要回到具体上下文中，告诉我下一步能做什么。

idle → 保存中 → 已保存 或 保存失败 内容冲突
这次定下的界面规则： 顶部统一展示“保存中 / 已保存 / N 项未保存”；右侧不重复展示正常状态，只在题目失败或冲突时保留处理入口。 问卷详情失败则从顶部直接重试。
05 / later

这套东西还没有“彻底完成”

现在已经可靠很多，但下面几件事仍值得留在脑子里。它们不是这轮必须解决的问题，也不应该被遗忘。

补上 Hook 级别的行为测试

服务端并发和冲突后的两个用户选择已经有 E2E；下一步更值得补的是防抖、连续输入与卸载时清理队列等更细的 Hook 行为测试。

编辑页仍保留初始化与发布编排

保存、结构变更、快照对账和题目锁已经拆成独立 Hook；权限检查、初始快照、发布与离开确认仍在页面里，后续可以继续按生命周期边界收敛。

AI 整卷生成仍跨两个提交边界

AI 题目已经通过批量事务做到整批成功或整批回滚；生成的问卷标题、描述仍会先走详情保存。若以后要求整份 AI 结果全有或全无，需要再合并这两个资源的事务边界。

自动化测试的 Windows 进程权限要固定下来

Playwright 卡在结束阶段的原因是受限环境无法终止 Next.js 子进程树；在允许进程清理的执行环境中可以正常退出。CI 和本地脚本应保持同样的权限前提。
