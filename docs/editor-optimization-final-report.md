# 问卷编辑器性能与协作可靠性优化总结

> 完成日期：2026-08-24  
> 测试环境：Next.js 16 / React 19 / 本地 PostgreSQL 18.3 / 本地 Soketi / 双浏览器双账号  
> 测试对象：问卷题目新增、实时同步、题目锁定与解锁、并发重排、断线恢复

## 1. 一句话结论

这次工作并不是单纯把一个慢接口改快，而是把“用户交互、数据库持久化、实时广播”从一条串行链路拆开，再为拆开后出现的并发与失败场景补上幂等、原子更新和快照对账。

最终结果是：本地 PostgreSQL 暖请求基准下，新增题目的可见反馈中位数由 **379.2 ms** 降到 **73.7 ms**；本地 Soketi 将服务端广播中位数由云端 Pusher 的 **220.6 ms** 降到 **6.4 ms**。双用户验收同时证明，锁定、解锁、离开释放、断线并发重排、重连收敛和连续新增均能保持一致。

## 2. 最初发生了什么

优化前，新增题目采用悲观串行流程：

```text
点击添加
  → 鉴权与权限检查
  → 统计题目数量
  → 写入数据库
  → 等待云端 Pusher 广播
  → 返回响应
  → 更新 Zustand
  → React 绘制
```

只要数据库跨区、权限查询或 Pusher 中任一步抖动，用户就会看到“点击后长时间没有反应”。最早的远程开发环境记录中，一次添加曾耗时 6～14 秒；分段计时进一步表明，等待主要发生在远端权限/数据库访问和同步广播，而不是 Zustand 更新或 JSON 解析。

切换到本地 PostgreSQL 后，问题被拆成了两类：

1. **交互链路结构问题**：页面必须等待整个服务端流程结束才给反馈。
2. **开发环境外部依赖问题**：云端 Pusher 的网络往返仍占据大部分服务端时间。

## 3. 第一阶段：让新增题目立即可见

提交：`f58a4a7 perf(editor): optimize question creation latency`

新的执行模型是：

```text
点击添加
  ├─ 立即插入临时题目 → Zustand → React 绘制
  └─ 后台串行持久化
       → 合并权限和计数查询
       → 数据库写入
       → 临时 ID 替换为正式 ID
       → 响应后广播
       → 失败则回滚临时题目
```

关键设计包括：

- 使用临时 ID 和“保存中”状态完成乐观更新；
- 使用持久化队列保护连续新增的顺序；
- 合并权限与计数查询，并为末尾追加提供单写入快路径；
- 将实时广播移出当前用户的响应关键路径；
- 保存成功后确认正式 ID，失败时撤销对应临时题目。

本地 PostgreSQL 的 5 次暖请求中位数：

| 指标 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 用户可见反馈 | 379.2 ms | 73.7 ms | **-80.6% / 5.15×** |
| 请求往返 | 301.4 ms | 74.5 ms | **-75.3% / 4.05×** |
| 服务端关键路径 | 210.3 ms | 17.5 ms | **-91.7% / 12.02×** |
| 数据库写入 | 6.0 ms | 2.8 ms | **-53.3% / 2.14×** |
| 点击到持久化完成 | 379.2 ms | 241.9 ms | **-36.2% / 1.57×** |

这组数据说明：用户体验提升的主要来源不是把 React 或 SQL 压榨到极限，而是把绘制提前到网络请求之前。

## 4. 第二阶段：给开发环境一条本地实时通道

提交：`c67b036 perf(realtime): add local soketi development path`

生产环境继续兼容 Pusher Cloud，开发环境可通过同一套 Pusher 协议切换到本地 Soketi。这样既保留了真实的 Presence、鉴权和事件语义，也消除了跨公网往返带来的噪声。

| 指标 | Pusher Cloud | 本地 Soketi | 变化 |
| --- | ---: | ---: | ---: |
| WebSocket 建连 | 450.4 ms | 54.2 ms | **-88.0% / 8.3×** |
| Presence 订阅 | 861.5 ms | 183.4 ms | **-78.7% / 4.7×** |
| 服务端事件发布 | 220.6 ms | 6.4 ms | **-97.1% / 34.5×** |
| 事件送达 | 158.0 ms | 72.0 ms | **-54.4% / 2.2×** |

这一阶段解决的是开发反馈速度和测量稳定性，不代表生产环境必须用 Soketi 替换 Pusher。

## 5. 性能优化引出的新风险

乐观更新和响应后广播缩短了等待，却也改变了系统的时序：客户端先变、数据库后确认、其他协作者再通过实时事件追上。如果只追求“快”，可能引入：

- 锁定或解锁误作用到其他问卷的同 ID/错误作用域；
- 重排只更新部分题目，失败后留下重复或不连续顺序；
- 自己的广播回显造成临时题目与正式题目重复；
- 广播丢失后，另一端永远停留在旧快照；
- 快速连续新增时，同一次 mutation 被重复执行；
- 首次进入页面自动选中第一题，却没有真正取得锁。

因此后续提交的目标不是继续追求更低的毫秒数，而是为新的异步模型建立正确性边界。

## 6. 第三阶段：并发与恢复语义加固

| 提交 | 作用 |
| --- | --- |
| `1a69881` | 将锁定、解锁和重排限制在当前问卷作用域，并用事务/原子更新保护顺序状态 |
| `99b33fa` | 为乐观创建增加 `clientMutationId`，让保存确认、广播回显和重试具备幂等身份 |
| `be64bc4` | 在重新订阅、页面恢复可见等场景拉取服务器快照，以数据库为最终事实来源完成对账 |
| `3b501d8` | 首次进入编辑页不再默认选中第一题，避免“看似正在编辑但没有锁”的假状态 |

现在的可靠性模型可以概括为：

```text
实时事件 = 低延迟增量通知
数据库快照 = 最终事实来源
clientMutationId = 跨临时 ID、正式 ID、广播回显的操作身份
事务与问卷作用域 = 服务端一致性边界
```

## 7. 双用户最终验收

验收角色：A 为协作者，B 为问卷所有者；两个不同账号同时打开同一问卷。

### 7.1 锁定、切换与离开释放

- A 点击第一题后，A 显示“我正在编辑”，B 显示 A 正在编辑；数据库只锁定该题。
- A 切换到第二题后，第一题解除、第二题锁定；任意时刻数据库最多只有一题被 A 锁定。
- B 点击被 A 锁定的题目不会取得编辑状态。
- A 离开编辑页后，B 的锁定提示消失，数据库锁定记录数回到 0。

结论：**通过**。

### 7.2 断线期间并发重排与重连收敛

- 停止 Soketi 后，A、B 在各自页面形成不同顺序。
- 两端分别提交相反重排，数据库仍保持唯一、连续的 `order`。
- 重启 Soketi 后，两端重新连接、订阅并触发快照对账。
- 最终 A、B 顺序均与数据库一致，没有重复题目。

结论：**通过**。这也解释了为什么切回休眠标签页或重连后会看到遗漏的题目：页面会主动拉取问卷快照进行修复，而不是凭空补出一条实时事件。

### 7.3 连续新增与幂等性

- 连续添加多道题后，两端题目数量一致，不残留“保存中”状态。
- 数据库最终共有 7 道测试题：7 个唯一正式 ID、7 个非空且唯一的 `clientMutationId`。
- `order` 连续为 `0...6`，没有重复顺序、重复题目或保存失败日志。

结论：**通过**。

### 7.4 验收矩阵

| 场景 | UI 结果 | 数据库结果 | 判定 |
| --- | --- | --- | --- |
| 首次进入编辑页 | 无默认选题 | 无新锁 | 通过 |
| A 锁定题目 | B 可见锁定人 | 仅目标题被锁 | 通过 |
| A 切换题目 | 旧锁释放、新锁取得 | 最多一条有效锁 | 通过 |
| A 离开页面 | B 清除锁提示 | 锁数量为 0 | 通过 |
| 双端离线并发重排 | 重连后顺序收敛 | 顺序唯一且连续 | 通过 |
| 连续新增 | 两端题目一致 | ID/mutation ID 唯一 | 通过 |
| Soketi 重启 | 自动重连并对账 | 以数据库快照收敛 | 通过 |

## 8. 这次优化的完整叙事

一开始，我们看到的是“添加题目很慢”；计时后发现，真正的问题是所有步骤被串在用户等待路径上。于是先通过乐观更新把交互反馈提前，再通过查询合并和快路径压缩持久化时间。随后，本地 PostgreSQL 暴露出云端实时服务成为开发环境的新主导延迟，因此引入兼容 Pusher 协议的本地 Soketi。

当系统变成“先本地、后持久化、再广播”后，性能问题转化成了分布式状态问题：锁属于谁、重排是否原子、自己的广播是否会重复应用、断线期间遗漏的变化如何找回。后续三个可靠性提交分别用作用域与事务、幂等 mutation ID、重连快照对账解决这些问题，最后通过双账号、断网和并发操作验证闭环。

因此，这次工作的价值不只是一个“80% 延迟下降”的数字，而是完成了从性能诊断、关键路径重构、开发基础设施本地化，到并发一致性和恢复机制验证的一整套工程闭环。

## 9. 边界与后续建议

- 本报告是同机开发环境相对基准，不应直接当作生产 SLA。
- 当前没有自动化 E2E 测试框架；这次结论来自分段计时、数据库检查和双浏览器手动验收。
- 生产环境仍需继续观测 Pusher 的失败率、发布延迟和响应后广播丢失情况。
- 下一步最有价值的是把本次锁定、离开释放、断线重排、重连对账和连续新增场景固化成 Playwright 测试。
