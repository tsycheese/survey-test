WHAT CHANGED

性能来自架构调整，而非隐藏等待

乐观更新必须同时解决临时状态、顺序、一致性和失败恢复；否则只是把错误推迟暴露。本次实现覆盖了完整生命周期。

即时但可回滚

临时 ID、保存中状态、正式 ID 确认和失败回滚共同保证本地状态可恢复。

快速但有顺序

用户可以连续添加，后台 Promise 队列按点击顺序持久化，避免并发顺序竞争。

查询与写入更少

权限与计数合并；末尾追加直接 create，中间插入才保留原子事务。

SCOPE & NEXT

结论边界

这是一组开发环境、同机相对基准。数据用于验证改造方向和量化相对提升，不替代生产环境的端到端监控与 SLA。

Pusher 服务本身不在本阶段优化范围。 基线中 Pusher 暖请求中位数为 188.7 ms，占服务端总耗时约 89.7%。优化版只是将广播移出当前用户的响应关键路径。下一阶段将单独比较云端 Pusher、开发环境禁用广播和本地 Soketi，并评估失败重试策略。

项目表述

数据需要保留测试环境限定，重点强调完整的一致性设计，而不只是“加了乐观更新”。

重构问卷编辑器题目创建链路，引入乐观更新、临时 ID、串行持久化、正式 ID 确认与失败回滚；合并权限/计数查询并为末尾追加设计单写入快路径。在本地 PostgreSQL 暖请求基准中，将用户可见延迟中位数由 379.2 ms 降至 73.7 ms（-80.6%），服务端关键路径由 210.3 ms 降至 17.5 ms（-91.7%）。
