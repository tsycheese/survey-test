# 问卷题目创建性能优化报告

> 测试日期：2026-08-20<br>
> 测试环境：Next.js 16.1.7（开发模式 / Turbopack）、React 19.2.4、PostgreSQL 18.3（`localhost:5432`）、Chrome DevTools<br>
> 测试范围：问卷编辑器在末尾新增 `TEXT` 题目的完整交互链路

## 1. 结论摘要

本次优化将“添加题目”从等待远端操作完成后再更新界面，改造成先在本地立即显示、再由后台可靠持久化的流程。在本地 PostgreSQL 环境下，5 次暖请求的中位数结果如下：

| 核心指标         |    优化前 |   优化后 |      降幅 |   提升倍数 |
| ---------------- | --------: | -------: | --------: | ---------: |
| 用户可见反馈     |  379.2 ms |  73.7 ms | **80.6%** |  **5.15×** |
| 请求往返         |  301.4 ms |  74.5 ms | **75.3%** |  **4.05×** |
| 服务端关键路径   |  210.3 ms |  17.5 ms | **91.7%** | **12.02×** |
| 数据库写入       |    6.0 ms |   2.8 ms | **53.3%** |  **2.14×** |
| 点击到持久化完成 | 379.2 ms¹ | 241.9 ms | **36.2%** |  **1.57×** |

¹ 优化前只有请求完成后才更新并绘制，因此“点击到绘制”也代表持久化完成后的可见时间。

本次优化最重要的结果不是单纯缩短 SQL 时间，而是将用户反馈与网络、数据库和实时广播解耦：题目能够在约 74 ms 内出现，即使后台保存发生抖动，主要编辑操作仍保持流畅。

## 2. 问题与根因

### 优化前执行链路

```text
点击添加
  → 等待鉴权
  → 查询问卷及协作者权限
  → 单独统计题目数量
  → 开启事务并写入题目
  → 同步等待 Pusher 广播
  → 返回响应
  → 更新 Zustand
  → React 绘制题目
```

原始实现属于悲观更新：数据库写入与 Pusher 广播全部完成之前，页面没有任何视觉反馈。任一外部步骤变慢，都会直接表现为“点击没有反应”。

本地 PostgreSQL 基线显示：暖请求数据库写入中位数只有 6.0 ms，而 Pusher 中位数为 188.7 ms，占服务端总耗时约 89.7%。因此 React/Zustand 和本地 PostgreSQL 都不是主要的用户等待来源，关键问题是整个流程被串联在同一条响应路径上。

### 优化后执行链路

```text
点击添加
  ├─ 立即插入临时题目 → React 绘制（用户关键路径）
  └─ 后台串行保存
       → 合并权限查询与题目计数
       → 末尾追加直接写入
       → 返回正式 ID 并替换临时 ID
       → 响应结束后触发 Pusher
       → 失败时回滚临时题目
```

## 3. 实施内容

### 3.1 乐观更新与临时 ID

- 点击后立即创建 `temporary-*` 题目并写入 Zustand。
- 题目在后台保存期间显示“保存中…”，并暂时禁止拖拽。
- 保存成功后用数据库正式 ID 原位替换临时 ID。
- 保存失败时删除临时题目、恢复顺序并提示用户。

### 3.2 串行持久化

- 多次快速添加仍会立即显示。
- 后台创建请求通过 Promise 队列串行执行，避免并发请求读取到相同题目数量而产生顺序竞争。
- 队列只约束持久化顺序，不阻塞乐观绘制。

### 3.3 服务端查询与写入优化

- 使用一次查询同时读取问卷所有者和题目数量。
- 所有者场景不再加载完整协作者列表。
- 非所有者仅通过复合唯一键查询对应协作者权限。
- 末尾追加题目直接执行一次 `create`；只有中间插入需要“后移 + 创建”事务。

### 3.4 Pusher 移出响应关键路径

- 创建成功响应不再等待 Pusher 完成。
- 广播在响应后执行，失败会记录日志，数据库仍是最终事实来源。

这只是关键路径调整，并不代表 Pusher 服务本身已完成优化。本地 Pusher/Soketi、开发环境广播策略及广播可靠性将在下一阶段单独评估。

### 3.5 开发连接池

- 开发模式保留少量 PostgreSQL 连接，降低远程数据库场景中连接反复建立的成本。
- 本报告的正式对比使用本地 PostgreSQL，因此数据库数据不受跨区域网络影响。

## 4. 测试方法

为控制变量，优化前后采用相同测试步骤：

1. 使用同一台电脑、浏览器和本地 PostgreSQL 18.3。
2. Pusher 均保持现有云端配置，不替换为本地实现。
3. 分别创建空白问卷，从末尾添加相同的 `TEXT` 题目。
4. 页面始终保持 `visibilityState = visible`。
5. 每个版本采集 1 次冷启动和 5 次暖请求。
6. 暖请求之间等待上一题保存完成，不进行快速连点。
7. 正式对比使用 5 次暖请求中位数；冷启动单独展示，不混入中位数。

测试使用 `performance.now()`、双 `requestAnimationFrame` 和 `Server-Timing` 分别记录交互、绘制与服务端阶段。计时日志本身会带来少量 DevTools 开销，因此结果适合用于同机相对比较，不应直接当作生产环境 SLA。

## 6. 冷启动观察

| 指标           |    优化前 |   优化后 |   变化 |
| -------------- | --------: | -------: | -----: |
| 点击到首次可见 | 5685.4 ms | 131.9 ms | -97.7% |
| 请求往返       | 5590.6 ms | 493.9 ms | -91.2% |
| 服务端计时     | 2415.6 ms |  43.4 ms | -98.2% |

冷启动会受到 Turbopack 首次路由编译、模块加载、连接初始化和 Pusher 冷启动影响，波动明显，因此只用于说明用户反馈与后台工作的解耦效果，不作为稳定吞吐结论。

## 7. 如何理解结果

### 用户体验改善是确定的

优化前必须等请求完成，用户约 379 ms 后才能看到题目；优化后约 74 ms 即可看到题目，已经进入接近即时反馈的范围。即使持久化仍需约 242 ms，用户也能看到明确的保存状态。

### 本地 PostgreSQL 不是主要瓶颈

原始版本的暖请求数据库写入只有 6.0 ms。服务端的大部分等待来自同步 Pusher，而非 PostgreSQL。本次服务端数据库优化仍将写入中位数降低到 2.8 ms，但它不是 80.6% 交互提升的唯一来源。

### React/Zustand 不是主要瓶颈

优化前 Zustand 更新中位数约 0.2 ms，状态更新到绘制约 66.7 ms；优化后乐观状态更新约 0.3 ms，点击到乐观绘制约 73.7 ms。渲染成本基本处于同一量级，真正的变化是渲染被提前到了网络请求之前。

### 数据一致性没有被牺牲

乐观更新同时配套了临时 ID、保存状态、串行队列、正式 ID 确认和失败回滚。它不是简单地“先显示不管结果”，而是一套可恢复的客户端事务流程。

## 8. 阶段边界与下一步

本阶段已经完成：

- 添加题目的即时反馈；
- 本地与持久化状态衔接；
- 快速连续添加时的顺序保护；
- 服务端查询与末尾写入优化；
- Pusher 从当前用户的响应关键路径移除。

下一阶段计划：

1. 单独测量 Pusher 首次广播和暖广播延迟；
2. 比较云端 Pusher、开发环境禁用广播和本地 Soketi；
3. 评估响应后广播失败时的重试/补偿策略；
4. 为快速连续添加增加队列长度与失败率观测。

## 9. 可用于简历的表述

> 重构问卷编辑器题目创建链路，引入乐观更新、临时 ID、串行持久化、正式 ID 确认与失败回滚；合并权限/计数查询并为末尾追加设计单写入快路径。在本地 PostgreSQL 暖请求基准中，将用户可见延迟中位数由 379.2 ms 降至 73.7 ms（-80.6%），服务端关键路径由 210.3 ms 降至 17.5 ms（-91.7%）。

该表述应保留“本地 PostgreSQL 暖请求基准”的限定，避免将开发环境数据误述为生产环境结果。
